Astra／Blender 的採用判斷

OpenAI 遊戲案例與建築案例確實採用 Blender／Python、既有素材與渲染檢查；Simon Willison 的實作還提供腳本、blend、執行紀錄與 skill。這支持一條可重跑的工作流，尚不足以稱精準 86 機甲全自動重建已成熟。細節與官方教學入口整理於Blender 工作流。

建議流程：現成模型 → 檢查輪廓／分件 → 小段 bpy 整理與材質 → 必要動作 → GLB → 遊戲內固定鏡頭驗收。Blender 是離線製作工具，玩家不需要安裝；先用 CLI，不把 MCP、Unity 或 Unreal 當前置條件。即時遊戲用 GLB；離線高畫質封面渲染是另一項工作，不混用其效能標準。

結論

《86》專屬模型與動作缺口

現已找到三個可下載且標示 CC Attribution 的《86》粉絲模型，故「沒有候選、必須從零建模」的原判斷不成立。它們應先進實檔驗收，再決定改造或重建。另找到 Ameise (EF-1) 的具體 Sketchfab 頁面，但本輪頁面回傳 cache miss，只能核實標題與網址，作者、下載狀態、授權、面數、格式及 rig 全部未知，因此暫列僅參考／待查，不能下載或納入製作。可旋轉 viewer 仍不能證明可改作或含骨架，也不應解包 viewer 取得資產。

CC Attribution 是上傳者對該模型檔的授權標示，不等於取得《86》原作角色與機體設計的商業授權；目前可用於內部技術 spike 與改造評估，對外發布前仍需另做權利審核。

Babylon glTF 管線判定

Babylon 官方文件目前示範以 ImportMeshAsync 載入 GLB，匯入結果中的動畫可透過具名 AnimationGroup 播放；純 ES module 路徑需要明確註冊 glTF loader。官方亦有 LoadSmartAssetAsync 以穩定 key 載入 glTF 並回傳 AssetContainer。這表示候選資產應先統一轉成 GLB，保留具名節點與 animation groups，再由資產容器實例化；不能只確認 viewer 能顯示就視為 Babylon 可直接量產。Babylon animated character、Babylon pure imports glTF、Babylon smart assets

這些 API 概念於 2026-09-08 透過 Context7 查核官方 Babylon.js Documentation；實作 spike 時仍需固定套件版本，並以該版本的官方 import 路徑驗證。

第一隻機體的素材驗收門

  1. 足鎖：idle、前進、側移、轉向與停止時足端不得明顯滑地；坡面 raycast 修正不可讓膝關節翻轉。
  2. 關節軸：每條腿的髖／膝／踝 pivot、局部軸與旋轉限制一致；縮放已套用，鏡像骨不帶負縮放異常。
  3. 砲口座標：主砲、機槍與特效 socket 有穩定名稱、方向與 local transform；後座動畫不改壞彈道起點。
  4. 受擊部位：機身、腿、武器與 Boss 部件可分 mesh 或具清楚節點，能綁簡化 hit proxy、材質閃爍與部件破壞。
  5. GLB／UV／PBR：GLB 可離線載入；UV 與材質對應正確；允許刻意鏡像重用，另行檢查烘焙接縫，base color、normal、metallic-roughness、AO／emissive 色彩空間正確，貼圖尺寸受預算控制。
  6. 動畫與 LOD：具名 animation groups 能循環／混合；至少兩級 LOD 保持砲口與碰撞代理一致，切換時輪廓、材質與骨架不跳動。

只有上述六項通過，候選才算合格的遊戲機體。近期最低成本路線是先下載並驗收 leoxx300 的 Juggernaut；若節點或拓撲不適合動畫，再用 Quaternius mech 驗管線。場景沿用 Kenney 道路／工業灰盒、Poly Haven 混凝土與低解析 HDRI，特效先重用本機 Kenney 四張煙霧 PNG 和 Sinestesia 兩張爆炸 atlas。實檔結果再決定修模、重拓撲或從零製作，不能先把後者當成既定成本。

多足動作改造方案

先驗收候選是否已按機身、髖、上腿、下腿、足與武器分件，並檢查每件 origin 是否位於真實轉軸。分件模型成本最低：建立一條腿的髖／膝／踝骨鏈後鏡像複製，將各剛性零件直接 parent 到對應骨，或以每件單一骨、100% 權重綁定；這能保住裝甲硬邊，避免自動權重把相鄰板件拉彎。Blender 官方也警告 Automatic Weights 在複雜、重疊物件上可能判錯，須人工修權重。Armature Deform Parent

合併模型必須先判定拓撲：若關節處已有獨立 UV 島與可分離面，可按連通件拆回零件、重設 pivot，再走上述剛性流程；若腿與機身焊成連續網格，則需切模、補內面、修法線／UV，或建立每關節互斥 vertex groups。後者最容易出現裝甲彎曲、穿插與貼圖接縫，成本可能接近重建，不能只靠「自動綁骨」估低。

每足配置 IK target 與 pole target，膝／髖再加旋轉限制；Blender 官方說 IK Solver 是骨骼專用約束，而 Limit constraints 用來限制關節自由度。Bone Constraints 可先製作 idle、前進、煞停、原地轉向四個短循環；用相位錯開的四足／六足擺動曲線產生程序步態，適合平地與緩坡的低速行走，也適合作為未取得原作動作時的技術替身。它不等於足鎖：坡面貼合、落腳點預測、機身速度突變、跨障礙與高速側移仍需執行時地形查詢、足端固定與重新落腳狀態機；未做實機 spike 前不能承諾無滑步。

輸出以 GLB 為交付，動作命名為 idle、walk、stop、turn。Blender glTF 官方只列物件 transform、pose bones 與 shape keys 為支援動畫；IK、限制與 driver 應在匯出時取樣／烘焙成骨骼 transform。各 Action 必須設為 active 或存入 NLA track，否則可能不會輸出；輸出後還要回匯 Blender並在 Babylon 驗 clip、循環、骨階層、尺度、足端軌跡與砲口節點。Blender glTF 2.0
